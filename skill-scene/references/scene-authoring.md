# 场景划分与场景文件写法

仅当要生成或调整场景划分时读本文件。

## 一、怎么切场景

**按「用户在做什么事」切，不按 skill 的类型切。** 类型分组（"都是设计类的"）在使用现场没有意义——判断"我现在在哪个场景"的是任务，不是标签。

四条判据：

1. **互斥**：一次任务应该只落进一个场景。两个场景的 description 让人犹豫该进哪个，就是切错了，合并或重划边界。
2. **穷尽**：每个 skill 都要有归属，或者被明确列入不归集清单。悬空的 skill 等于失踪。
3. **颗粒度**：一个场景 5 到 15 个 skill。少于 5 个考虑并入邻近场景；多于 15 个说明这个领域还能再分。
4. **总数**：场景总数控制在 12 个以内。场景本身是要付注入成本的，场景太多就退化回了原问题。

## 二、同职责的两套怎么办

装了多个 kit 时，经常出现同一件事有两套 skill（例如一套外来的开发流程 skill，和用户自己的一套）。

**场景内只收一套，另一套列入不归集清单。** 两套同时在场，每次路由都要做一次无谓的选择，这是注意力稀释而不是能力叠加。

取舍交给用户，不要自己拍板。把冲突组拿给用户看：哪几个是同职责、各自的来源、建议保留哪套及理由。用户定了再写进方案。

有一类例外值得单独捞回来：两套之间**确有互补的实操能力**。比如一套讲的是诊断纪律，另一套带了跑测试套件、看覆盖率的具体步骤，后者不构成重复，应当保留。判断依据是职责是否真的重合，不是名字像不像。

## 三、不归集的 skill

两类 skill 不进任何场景，直接打标退出注入：

- **被替代的**：上一节取舍中落选的那套。
- **纯占位壳**：description 写的是"仅当显式指定时使用，请改用 X"这类转发说明的。它们不提供任何能力，却和真 skill 一样按份收注入费。转发目标已经在某个场景里的话，壳子可以直接退休。

这两类仍然保留 `/skill-name` 手工调用，只是模型不再自动选中它们。

## 四、`scenes.json` 格式

归类方案落成这个文件，交给 `scene-tool.ts apply` 执行。

```json
{
  "scenes": [
    {
      "slug": "software-delivery",
      "title": "软件交付主流程",
      "description": "从需求到合并的软件开发主流程：写 PRD、需求分流、技术 spec、coding plan、建 worktree、查代码事实、评审门、合并收尾。要动代码或写项目文档时进入本场景。",
      "skills": ["dw-prd", "dw-workflow", "dw-worktree", "dw-code-facts", "dw-review-gate"]
    }
  ],
  "unassigned": [
    { "name": "ak-plan", "reason": "与 dw-workflow 同职责，用户选择保留 dw-*" },
    { "name": "lark-minutes", "reason": "纯占位壳，转发目标 lark-meeting 已在 scene-lark-collab" }
  ]
}
```

字段约束：

- `slug` 只用小写字母和连字符，最终目录名是 `scene-<slug>`。
- `description` 是这个场景实际注入的文本，写法见下一节。
- `skills` 用 skills 目录下的目录名，不是 frontmatter 里的 `name`（两者可能不一致，例如目录叫 `ak-seo` 而 name 是 `ak:seo`）。
- `unassigned` 每项必须写 `reason`。没有理由的排除，日后没人敢动。

## 五、场景 description 怎么写

场景的 description 是整套机制里唯一还参与自动路由的文本，它的触发质量直接决定归集后好不好用。

**触发质量的判据在 `skill-principle` 的原则 1.2**（what / when / 排除子句、覆盖真实措辞、堆砌阈值），写之前按那份执行，此处不复述。

场景 description 特有的两条：

- **写任务，不写 skill 清单。** 清单在正文里，写进 description 只会挤占触发信号。反例："包含 dw-prd、dw-workflow、dw-worktree 的开发场景"——用户不会用 skill 名字开口。
- **末尾给一句进入条件。** 例如"要动代码或写项目文档时进入本场景"。场景之间靠这句划边界，比靠关键词可靠。

## 六、场景 `SKILL.md` 模板

场景目录里**只有这一个文件**。清单用相对链接指向原件，不要复制、不要做软链。

```markdown
---
name: scene-<slug>
description: "<按上一节写>"
---

# <title>

<一到两句：这个场景覆盖什么任务，边界在哪。>

## 本场景的 skill

| skill | 用途 |
|-------|------|
| [dw-workflow](../dw-workflow/SKILL.md) | 开发主流程：分流、spec、coding plan、测试方案 |
| [dw-worktree](../dw-worktree/SKILL.md) | 任务开始前建 worktree，全部门禁通过后合并 |

按当前这一步的需要读取其中一两个，不要全部读入。

## 不在本场景的

需要的能力不在上表里时：

- 只要那一个 skill 的内容，直接 `Read ~/.claude/skills/<skill-name>/SKILL.md`。
- 整段工作要转到另一个领域，先读 `../skill-scene/SCENE-INDEX.md` 查它属于哪个场景，再进那个场景。
```

表格第二列写**用途**，不要抄原 skill 的 description。原 description 是为了让模型在上百个候选里做匹配而写的，进了场景已经不需要那些触发词；这里要的是"选它还是选隔壁那个"的区分度，一句话即可。
